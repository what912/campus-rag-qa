# 基于大模型RAG的校园知识问答系统设计与实现

内容草稿日期为2026年10月13日。本稿根据当前代码和保存的运行记录编写，供本人理解、修改和与导师讨论。学院本届论文模板尚未提供，正文结构和排版需要按最终要求调整。正式独立测试与人工复核尚未完成，实验部分只报告已有开发记录，不填写尚未测得的准确率或提升幅度。

## 摘要

校园教学信息分散在培养方案、课程大纲和办事文件中，学生查询时需要理解不同文件的版本、专业及入学年级。本文设计并实现面向中国传媒大学本科教学资料的知识问答系统。系统采用Python与FastAPI提供本机服务，以SQLite保存文档、片段和来源信息，完成PDF、Word、HTML及文本的解析、切片和必要的扫描识别；使用TF-IDF和BGE中文语义向量进行检索，并通过兼容接口调用大模型生成带来源编号的回答。系统保留纯词面、纯语义及RRF混合检索，新增结合问题重点、文件主题和信息类型的规则重排序。页面同时展示文件命中和证据片段命中，并支持对保存的模型回答逐题评分。当前知识库包含7份实际资料和4份明确标注的示例，正常问答排除示例。开发检查暴露出检索漏检、对照背景不一致和适用范围说明过多等问题，据此进行了优化。系统已形成可运行的文档检索与证据生成链路，正式效果结论仍需独立题集和人工评分支持。

关键词为检索增强生成、校园知识问答、中文语义向量、混合检索、证据溯源。

## 第1章 绪论

### 1.1 研究背景与问题

本科生办理在读证明、查询成绩单、了解学位条件和阅读专业培养要求时，往往需要在多个文件中寻找条款。文件既可能是多页PDF，也可能是包含表格和图片的网页。同一事项还可能涉及不同发布日期、专业或入学年级。单纯按文件名搜索通常只能找到文件，仍需人工定位内容。直接向通用大模型询问则难以确认回答是否来自指定学校和指定文件。

本项目将校园领域资料组织为可更新的本地知识库，把查询过程拆分为检索和生成两个环节。检索结果必须提供文件名、版本和位置，生成回答也应当能回到相应片段。研究目标是完成可用的工程原型，并用真实记录分析查询失败发生在哪个环节。

### 1.2 研究范围与目标

系统服务范围为中国传媒大学通用本科教学办事文件，以及2023级计算机科学与技术专业资料。五份公开文件涉及学籍、转专业、学士学位、在读证明和成绩单；用户提供的2022版培养方案经本人确认2023级沿用，课程大纲经本人确认来自任课教师或教务。上述确认作为来源元信息记录，不等同于系统独立核验了所有文件的现行效力。

目标包括文档导入与解析、可追溯切片、词面及语义检索、专业年级筛选、证据约束生成、原件查看、实验记录和回答核对。系统以单人本机运行和毕业设计演示为交付范围。课程大纲当前覆盖五门课程，不能据此宣称已覆盖学校所有课程。

### 1.3 本文工作与组织

本文的工程工作包括异构资料处理、基于元信息的检索筛选、三种基础检索与规则重排序、兼容生成接口和引用检查，以及证据层面的统一评估。论文先介绍相关技术，再说明需求与数据模型，随后给出实现流程和验证记录，最后分析局限与后续改进。

## 第2章 相关技术

### 2.1 检索增强生成

Lewis等人的研究将可检索的外部知识与生成模型结合，讨论知识密集任务中的生成与来源问题。[1] 本项目采用固定语义编码器和在线生成接口，先从本地文件检索，再把问题及片段送入生成模型。实现重点是校园资料组织和证据约束，不进行生成模型训练。

检索能否提供目标条款决定了生成环节的输入范围。当相关文件已经存在但正确条款没有进入前几个片段时，模型仍可能无法回答。因而需要分别评价检索和回答，并保留每次真正发送的上下文。

### 2.2 词面检索与中文语义向量

TF-IDF以词项在当前片段集合中的出现情况构造稀疏向量。本项目采用中文字符二至三元组，避免额外依赖分词词典，最大特征数为30000。它能直接利用课程名、材料名称和特定词组，但对改写问法和跨词表达存在限制。

语义检索使用BAAI发布的bge-small-zh-v1.5。[3] 当前运行记录显示向量维度为512，查询使用中文检索指令，文档使用无额外指令的编码。归一化向量通过点积计算余弦相似度。模型本地运行在CPU上，不调用外部Embedding服务；生成阶段才调用远程模型。

相似度阈值属于检索配置，不能解释为回答正确的概率。当前TF-IDF阈值为0.08，语义阈值为0.55，两个数值分别适用于对应表示空间。

### 2.3 排名融合与规则重排序

RRF根据不同检索器返回的排名融合候选，避免直接相加尺度不同的相似度。其贡献可表述为每个系统中的候选排名与常数相加后取倒数，再跨系统求和；原研究使用常数60。[2] 本项目保留该方法作为混合检索基线。

开发中发现，模板性文字可能因同时出现在词面和语义候选中而排在具体条款之前。因此新增hybrid_rerank策略，先对问题中的通用表达和资料主题进行分离，再结合重点词面匹配、文件名主题、RRF分数和所问信息类型排序。例如“在哪个学期组织”关注学期类型，“什么时候施行”关注施行条款；规则不保存具体题目的答案，也不按题号返回固定结果。

当前排序的四项权重分别为0.25、0.20、0.15和0.40。它们依据开发题诊断确定，属于需冻结和独立验证的配置。该策略为领域规则重排序，未使用交叉编码器模型，不能将其写成神经重排序训练成果。

## 第3章 系统需求与设计

### 3.1 使用场景与功能需求

学生输入自然语言问题后，系统应先根据分类、专业与年级筛选资料，再检索相关片段。证据足够时生成中文回答并标注来源；当前检索未覆盖目标内容时提示无法确认。回答右侧展示原文片段，用户可以下载原件核对。文档管理应支持导入、哈希去重、浏览、下载和删除。

毕业设计还需要实验能力。系统应保存真实模型回答、检索上下文、接口返回用量、模型标识与时延。页面的文件命中与证据命中应区分展示。人工核对页面应允许逐题查看四组回答和原文、记录评分人及意见，而不因打开页面重新调用模型。

### 3.2 非功能需求

系统适配本机CPU环境，运行入口应简洁。资料和向量留在项目目录；外部调用失败要给出明确提示。凭据不应出现在普通配置、页面响应、实验结果或交付包中。处理文件需要限制格式、大小与解析工作量，资料更新后能重建索引。

本机版不提供多人身份和文档权限。若扩大为公开服务，需要重新设计认证、权限、限流和后台索引任务，这些不属于当前已完成的部署功能。

### 3.3 总体架构

系统由页面、FastAPI接口、文档处理、知识库、检索、生成服务适配和实验评估组成。文档解析后的片段进入SQLite和向量索引；用户问题经过共享的类别路由和适用范围筛选后进入检索；生成模块只接收检索得到的片段。回答与来源一同返回页面。

架构图见本稿插图。文档管理和问答使用同一知识库，检索检查与离线实验使用同一证据评估函数，降低页面口径与论文脚本口径不一致的风险。

### 3.4 数据模型

documents表保存文档标识、名称、分类、版本、来源、示例标记、SHA-256、导入时间、原件路径和元信息。chunks表保存片段标识、所属文档、序号、文本、文件页序号及标题。metadata表保存种子资料导入等内部状态。专业、入学年级、发布日期、来源性质和仅参考标记放在文档元信息中。

用户评分独立保存为JSON，与实验文件哈希绑定。每条评分通过题号和方案定位，包含正确性、证据支持、引用支持与说明。助手初评使用单独文件和明确角色标记，不能自动填入人工评分栏。

### 3.5 主要接口

| 接口 | 作用 |
|---|---|
| GET /api/status | 查看文档、片段、检索与模型状态 |
| GET及POST /api/documents | 列出资料或导入文档 |
| GET及DELETE /api/documents/{id} | 浏览片段或删除对应资料 |
| POST /api/ask | 检索并回答问题 |
| GET及PUT /api/settings | 查看或更新非明文密钥配置 |
| GET /api/evaluation | 使用当前问答配置检查开发题证据 |
| GET /api/experiments | 列出已保存的模型实验 |
| PUT /api/experiments/{filename}/review | 保存与原记录哈希对应的用户评分 |

## 第4章 系统实现

### 4.1 文档解析与可追溯切片

PDF保留文件页序号，默认采用pypdf提取文本；遇到异常字体编码时尝试PyMuPDF。文字不足的页面可启用RapidOCR，识别结果保留OCR标记，数字和复杂版面仍需要核对。Word按照段落与表格顺序读取；HTML提取正文、标题和表格，不执行脚本；文本文件支持UTF-8及GB18030。

当前切片上限为400字符，重叠最多60字符，并保留页码与标题。课程标题在跨页时传递，防止后一页内容失去所属课程。字符数与模型token数不同；当前语料检查中最长片段为376个模型token，低于模型的512上限。之后新增资料仍需检查截断情况。

HTML课程地图属于图片，当前没有转换为可检索的课程关系。系统保存原资产并提示这一限制。培养方案个别学分与比例存在原文数字关系待核对的问题，解析模块保留原文，不自行用计算值替换正式文字。

### 4.2 适用范围和检索实现

默认范围为2023级计算机科学与技术。问题明确提出其他入学年级时按问题处理。仅参考资料与默认排除的示例不参与检索。字段未指定专门年级或专业时，仍需结合正文适用对象判断，不仅凭空字段就推断文件不适用。

类别路由区分专业学分、具体课程考核与通用课程成绩制度。前两者分别查培养方案和课程大纲，通用成绩比例由谁确定则查办事流程。路由由campus/routing.py提供，问答与评估共同使用。

基础检索使用TF-IDF或BGE余弦分数；混合策略融合两类候选。新增重排序进一步突出所问细节和信息类型。原有策略保留用于对照，新增策略在页面设置中可选，避免把优化后结果追溯写入旧运行记录。

### 4.3 生成接口与证据约束

生成模块使用兼容Chat Completions的协议，当前接入DeepSeek。保存记录中的实际模型标识为deepseek-flash，温度0.1，每次最多输出1400个token。请求包括用户问题、学校与专业年级背景、带编号的检索片段和约束说明。接口返回usage、response_id及结束原因供记录。

提示要求每条实质结论使用对应来源编号，不执行资料中的指令，不补充文档没有支持的校园规定。输入明确为片段而非全文，检索未覆盖时不能断言完整文件没有规定。对不同版本、专业或年级的冲突按正文说明。

模型未引用来源、使用不存在的编号或达到输出长度限制时，程序返回提示。此类机械检查不能证明引用的片段支持对应结论，需要进一步逐条评价。

### 4.4 凭据与异常处理

密钥可仅在进程中使用，或由Windows DPAPI按当前用户加密保存。普通配置只保存是否启用等非秘密字段，读取设置不返回密钥。不同API来源之间不自动复用旧凭据。跨电脑迁移需要重新配置本人密钥。

文件上限为10MB，提取文字最多50万字符，每份PDF最多300页，自动OCR最多处理20个扫描页。空文件、重复文件、错误格式、模型路径错误、接口超时和授权错误都有明确提示。当前服务仅监听127.0.0.1。

### 4.5 检索检查与回答核对页面

新的检索检查默认返回前4条片段，使用与问答一致的分类、范围和检索策略。正确文件命中作为辅助信息，正确证据命中、平均片段Recall和MRR单独展示；标签无法对应原文时明确标记，不把缺标签条目当作正确。

回答核对页面读取已保存实验，每题显示四组原始回答与来源。用户填写评分人、正确性及证据和引用支持意见，保存时检查题号、方案和原始文件哈希。页面还支持导出评分CSV，问答结果可复制或导出含原文的Markdown记录。打开核对页面不会发送新的生成请求。

## 第5章 测试与开发分析

### 5.1 环境和语料

运行环境为Windows、Python3.12和CPU，完整依赖版本记录于requirements-lock.txt。当前资料库包含11份文档、134个片段，其中7份为实际资料，4份为明确标记的虚构示例。正常问答和开发实验排除示例。文档原件、来源及SHA-256分别保存，模型revision和下载信息也保留。

自动检查覆盖文档解析与OCR、上传和删除、重复检测、版本范围、密钥加密及重启恢复、接口响应、证据评估和评分持久化。具体测试次数以当次保存的验证记录为准。自动功能测试通过说明所测功能符合预期，不等同于生成回答正确率。

### 5.2 开发题与检索指标

19道通用问题已经由本人核对标签并参与开发；4道无依据题按本人要求删除。每题通过指定文件、页码和证据文本对应已标注片段。正确证据命中表示前K条中至少存在一条标注证据；片段Recall表示找到的标注片段占全部标注片段的比例；MRR描述首条正确证据的位置。文件命中只能说明来源文件相符。

| 开发方案 | 平均片段Recall@4 | MRR |
|---|---|---|
| TF-IDF | 0.8947 | 0.8684 |
| BGE语义 | 0.8158 | 0.5921 |
| RRF混合 | 0.8421 | 0.7719 |
| 问题重点规则重排序 | 1.0000 | 0.9737 |

新增排序使当前19题的标注证据均进入前4条。这些题已用于诊断和规则设计，因而上述结果只说明开发集上的修复情况，不能证明独立测试泛化或生成准确率。当前没有无依据题，不报告未测试的无依据拒答率。后续独立结果完成前，本表不得改称正式性能比较。

### 5.3 已执行的模型开发对照

已执行19题四组开发记录，共76条结果，实际75次DeepSeek生成请求成功，另1条为未达到语义证据阈值的本地提示。原始记录保留73次调用；通用成绩规则路由修正后，TF-IDF与混合组各补一次，累计75次。接口返回总token为73731。

该批直接回答提示遗漏学校名称，而RAG可从资料得知学校；四组还按组顺序执行，修正记录含开发后路由变化。因此本批用于连接验证、用量记录和失败分析，不用于RAG提升幅度或方案准确率排名。后续脚本已经统一学校背景，并加入可复现的问题顺序与组间顺序平衡，旧回答保持不变。

对57条RAG结果的助手初评只核对目标核心事实，直接组由于背景不一致未给出效果分。助手初评与用户评分分别保存，尚未形成独立人工审核数据。有效的来源编号也不能替代证据支持评价。

### 5.4 失败案例与改进

证明代办问题的原始语义和混合检索没有返回代办所需材料的条款；施行日期问题的部分方案返回了修订通知及学位条件，却漏掉附则；转专业学期问题中，关于工作通知和培养方案的片段排在学期条款之前。文件都已存在，失败主要发生在候选排序或阈值阶段，不需要重复提交同一原件。

这些情况说明检索评估必须定位到条款。规则重排序将问题重点与文件主题分离，并识别时间或委托等信息类型；生成提示则提醒片段与全文的区别，减少把漏检解释为全文无规定的表达。

### 5.5 正式实验计划

另拟20道专业候选题，其中8道培养方案、12道课程大纲题。候选题保存原文位置、证据、参考答案和源文件哈希；尚未独立人工审核，没有运行检索调参或模型请求。正式使用前需要检查与开发场景的重合并确定划分。

冻结工具保存题集、数据库快照、原件、提示、配置、执行顺序与代码哈希。候选标签未审核时不得执行正式快照生成。20题四组计划最多80次生成请求，但本次只准备计划，未执行；后续请求次数和额度需另行确定。

正式评价需同时报告检索证据、回答正确性、关键条件遗漏、引用支持、版本适用和耗时。评分应记录实际人员及复核流程。远程服务的内部模型版本和缓存仍可能变化，response_id及日期有助于追溯，不能保证严格复现其内部计算。

## 第6章 总结与后续工作

本项目完成校园资料导入、解析、切片、本地向量化、范围筛选、检索、证据生成及原文展示。针对开发中发现的漏检和评估口径问题，新增规则重排序、共享证据评估和保存结果的核对页面。系统保留旧记录及其方法限制，能够从文件和片段层面分析问答失败。

当前范围较小，资料版本的过渡条款仍需人工理解；图片课程地图没有进入结构化检索；规则词表及排序权重需要独立验证；正式回答评分尚未完成。后续优先完成题集审核、冻结对照与人工复核，再研究更通用的重排序和结构化课程关系。公开多人服务的权限和运行保障应在需求明确后另行设计。
